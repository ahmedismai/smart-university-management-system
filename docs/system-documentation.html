1. Executive Summary & Vision

OVERVIEW

The Smart University Management System (SUMS) is an enterprise web application designed to consolidate, automate, and centralize every aspect of university operations into a cohesive, high-performance platform. It eliminates fragmented departmental spreadsheets, paper-based records, and legacy isolated databases by providing real-time synchronization between academic records, student services, financial auditing, and administrative governance.

Strategic Institutional Objective: Deliver a fast, responsive, role-based platform that guarantees sub-second responsiveness, real-time classroom interactions, automated grade transcripts, and tamper-proof financial tracking.

Core Functional Pillars

  • Role-Based Access Control (RBAC): Segmented authenticated portals designed specifically for Administrators, Faculty (Teachers), Students, Staff, and Parents.
  • Curriculum & Routine Automation: Automated schedule routine management, room allocation, class capacity enforcement, and multi-criteria attendance tracking.
  • Financial Engine & Invoicing: Invoicing, waiver subsidies, overdue fine calculations, and multi-method payment verification.
  • Campus Auxiliary Services: Digital library management with 14-day borrowing controls, real-time student-faculty chat, hostel allocation, and transport coordination.

2. Architecture & Technology Stack

TECH STACK

The system is constructed as a high-efficiency modular monolith leveraging server-side rendering (SSR), edge compute, persistent document stores, and standalone WebSocket micro-threads.

Edge Security & Auth Next.js Edge Middleware Multi-role session cookie verification at the network edge prior to page or API execution.

3. System Requirements Specification

REQUIREMENTS

3.1 Functional Requirements

  • Authentication: Secure authentication handling password hashing (`bcryptjs`) and setting signed HTTP-only cookies.
  • Academic Management: Full CRUD operations over Classes, Courses, Sections, and weekly Lecture/Lab Routines with collision detection.
  • Attendance Governance: Daily attendance logging linked with automated absenteeism tracking governed by institutional thresholds.
  • Examinations & Transcripts: Batch marks upload, dynamic transcript generation, GPA computation, and result distribution.
  • Library Management: Tracking available copies, 14-day loan terms, automated overdue fine calculation, and renewals.
  • Lectures: Teachers upload PDF/DOC/DOCX lecture files (max 4 MB) per course and section; students download only their own section's files.
  • Per-Course Marks & CGPA: One mark per student, course and assessment (upsert); credit-weighted CGPA from the grade scale; CSV upload and graduation-clearance check.
  • Requests & Inquiries: Contact, leave and password-reset requests are stored and handled by admins; students keep documents and print an ID card.
  • Payment Verification & Notifications: Card payments are instant; wallet/bank payments wait for finance approval; decisions and reminders notify the student.
  • Campus Operations: Admin CRUD for students, staff, parents and users; inventory audits; hostel allocation; global search; dark mode; all amounts in EGP.
  • SUMS Assistant: Chatbot (Gemini with offline fallback) that answers from the university knowledge base and the signed-in student's real records.
  • New data models: Lecture, StudentDocument, Inquiry, Notification, InventoryAudit, InventoryLog, Meeting, Application, RolePermission (40 models in total).

3.2 Non-Functional Requirements

  • Sub-Second Latency: Server-side rendering ensures primary dashboards render within 250 milliseconds.
  • Information Security: Complete isolation of student data; administrative operations audited with timestamps.
  • Fault Tolerance: Independent Socket.io server ensures real-time messaging does not impede core database transactions.

4.3 Sequence Diagram (Student Session Lifecycle)

SEQUENCE DIAGRAM

The Sequence Diagram chronologically traces an active student session across all tiers: Student Client → Student Portal UI → Edge Middleware → API Route Handlers → MongoDB → Socket.io Server → Teacher Client.

Figure 4.3: End-to-End Execution Sequence Across Architectural Tiers
📄 Vector PDF 🌐 Interactive HTML

Sequential Stage Breakdown

  1. Authentication Flow: Credentials submitted via POST /login, verified against MongoDB via bcrypt.compare, followed by signed cookie dispatch (`student_session`).
  2. Protected Route Verification: middleware.ts intercepts requests to /student/dashboard, verifying cookie existence before rendering.
  3. Library Borrowing Logic: Evaluates active loan count (< 5), verifies copy availability, decrements stock, and generates a BookIssue record.
  4. Financial Settlement: Student executes payment; the transaction updates the record to Paid and returns a verifiable transaction ID.
  5. Real-Time Chat Transmission: Student connects to Socket.io (Port 3001), emits sendMessage, saves record in MongoDB, and streams event to Teacher.

Workflow Path Summary

  • Visitor Branch: Visitors choose to explore public academic catalog pages or apply for admissions, terminating cleanly without session overhead.
  • Authentication Gateway: Invalid credentials trigger an HTTP 400/401 notification toast and an immediate retry branch.
  • Student Task Execution: Enables concurrent pathways for checking academic records, processing fee payments, executing book loans, or chatting.

6. Security, RBAC & Deployment Guide

GOVERNANCE

6.1 Security & Route Protection (`middleware.ts`)

All incoming requests to protected routes (`/admin/*` and `/student/*`) are evaluated at the edge by Next.js Middleware. Missing or invalid session cookies result in immediate redirect to the designated portal login, securing administrative and confidential student records.

6.2 Installation & Startup Procedure

To execute the platform in local or staging environments, run the following commands: 

# Step 1: Install production and dev dependencies
npm install

# Step 2: Establish local environment variables in .env.local
# MONGODB_URI=mongodb://localhost:27017/sums_db
# JWT_SECRET=your_production_secret_key
# NEXT_PUBLIC_SOCKET_URL=http://localhost:3001

# Step 3: Launch the dedicated WebSocket Server (Port 3001)
node socket-server.js

# Step 4: Launch the Next.js Web Application (Port 3000)
npm run dev

System Verification Notice: The web application connects to the MongoDB instance and communicates with the real-time Socket server at http://localhost:3001.

6.3 Deployment (GitHub + Vercel)

  • Website and API: push to GitHub and import the repository in Vercel (vercel.json included). Set MONGODB_URI (optionally GEMINI_API_KEY, AI_MODEL_NAME, NEXT_PUBLIC_SOCKET_URL) and allow Vercel in MongoDB Atlas Network Access.
  • Socket server: hosted separately (Render, Railway or Fly.io) because Vercel cannot run WebSockets.
  • Upload limit: 4 MB per file (Vercel request body limit is 4.5 MB).
